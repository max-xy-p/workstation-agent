# 会话与消息管理

后端提供会话的创建、列表、详情、更名和删除，以及文本消息的新增、分页读取、详情、编辑和删除。
这些能力供前端或其他通信适配器调用，不会因为保存或修改一条文本而自动运行 Agent。
运行状态、取消和审批恢复继续使用 [Agent HTTP 服务](agent-service.md) 的接口。

## 使用前提

先按 [PostgreSQL 部署说明](database.md) 配置数据库，运行 `uv run workstation-agent init-db`，
再启动 `serve-agent`。已有 PostgreSQL 数据会通过新增的版本 6 迁移建立会话和消息表，不清空原有表。
首次通过授权的业务写入也会检查迁移；读取接口不会自动建表。
所有会话与消息接口沿用 HTTP 服务的 Bearer 令牌、Host 和 Origin 检查。

会话 ID 只能包含 1–128 个字母、数字、下划线和连字符。
身份、工作区和项目范围来自服务配置，客户端不能通过请求扩大访问范围。

## 会话接口

| 方法与路径 | 请求及结果 |
| --- | --- |
| `POST /sessions` | JSON `{"title":"调试项目"}`，标题可省略，默认“新会话”；返回 201 和新会话 |
| `GET /sessions?limit=50&offset=0` | 按更新时间倒序分页，时间相同时按 ID 排序 |
| `GET /sessions/{id}` | 返回 ID、标题、版本号 `revision`、创建和更新时间 |
| `PATCH /sessions/{id}` | JSON `{"title":"新的标题","revision":0}`；返回更新后的会话 |
| `DELETE /sessions/{id}?revision=0` | 删除该会话、其文本历史和框架检查点；返回被删除的 ID |

标题最多 200 个字符，不得为空白。新会话的版本号为 0；新增消息、修改标题或历史都会增加版本号。
修改前先读取会话，把读到的 `revision` 原样传回。版本不一致返回 409 和 `revision_conflict`，
此时应重新读取，再让用户决定如何修改，不能直接用新的版本号盲目重试。

列表页长 `limit` 为 1–100，默认 50；`offset` 为 0–100000，默认 0。
结果为 `{"items":[...],"next_offset":50}`，没有下一页时 `next_offset` 为 `null`。
分页不固定数据库内容；有并发更名、新消息或删除时，重新从第一页读取可以得到当前排序。

## 消息接口

| 方法与路径 | 请求及结果 |
| --- | --- |
| `POST /sessions/{id}/messages` | JSON `{"content":"背景说明","revision":0}`；只保存用户文本，返回 201 和新消息 |
| `GET /sessions/{id}/messages?limit=50&offset=0` | 按消息位置升序分页，分页结构与会话列表相同 |
| `GET /sessions/{id}/messages/{message_id}` | 返回消息详情，不允许跨会话读取同一消息 ID |
| `PATCH /sessions/{id}/messages/{message_id}` | JSON `{"content":"改写的问题","revision":2}`；只允许编辑用户消息 |
| `DELETE /sessions/{id}/messages/{message_id}?revision=2` | 删除所选消息及其后续消息，返回 ID 和 `following_messages_deleted: true` |

消息包含 ID、所属会话、排序位置 `position`、角色 `role`、文本、关联运行 ID 及创建和更新时间。
位置号只保证排序，删除后不会重新编号。手工新增的用户文本没有运行 ID。
文本最多 32000 个字符，不得为空白；HTTP 正文仍受整个请求 65536 字节的限制。
普通消息写入接口不能指定角色或伪造助手答复；只有 Agent 完成任务后才保存 `assistant` 消息。
工具调用参数、工具输出、模型内部消息和上下文摘要不会复制到这个消息列表。
写入前清除配置中已知的凭据，通用敏感内容识别仍受现有脱敏规则限制。

编辑用户消息时，程序保留该条消息并修改正文，删除它后面的全部消息。
删除消息时，程序删除所选消息及其后面的全部消息。
这两种操作都清除整个会话的框架检查点、上下文摘要及任务状态栏，
让下次运行从保留下来的用户文本和最终答复重新构造上下文。
旧工具结果不会被重建成模型可执行的工具调用；历史修改也不会撤销已发生的外部操作。
助手消息不能直接编辑，尝试编辑返回 409 和 `message_read_only`。

## 与运行入口的关系

前端发送需要 Agent 回答的新问题时，直接调用 `POST /runs`，传入 `task` 和 `session_id`。
应用会自动建立缺失的会话、保存用户消息，任务完成时再保存最终答复；审批恢复沿用原运行 ID，不重复插入用户消息。
**不要先调用消息新增接口保存同一问题，再把同一正文提交到运行入口，否则会成为两条用户消息。**
消息新增接口用于单独补充历史文本。编辑历史后，重新运行仍需显式提交新的任务，例如“根据上面修改后的问题继续回答”。
普通 CRUD 不负责决定何时调用模型，也不自动重新执行工具。

运行中的会话由数据库锁保护，历史写入和删除返回 409 与 `session_busy`。
会话等待审批时也不能追加、修改或删除历史，重启服务后此限制继续生效；先通过审批接口恢复或拒绝待审批项。
空闲会话可以更名；等待审批时更名不影响审批内容，仍需传入正确版本。
读取会话和消息不要求 Agent 空闲，因此前端可以在运行期间同时读取已保存的用户文本和运行进度。

删除会话不删除长期记忆、RAG 文档、外部文件或独立的 Run 结果归档。
当前服务进程保留的运行查询记录仍按其原有容量规则管理，它们与持久文本历史是两个不同的数据集合。
CLI 的 `session clear` 同时清除会话文本与检查点，保留会话元数据；此命令仍须显式授权删除。

## 错误与一致性

不存在的会话或消息返回 404；非法请求返回 422；版本冲突或会话忙碌返回 409。
数据库未配置或暂不可用返回固定的 503 错误，不返回连接地址、SQL 或底层异常。

文本的修改和后续消息的删除在同一数据库事务内完成，写入失败时一起回滚。
框架检查点由官方 `PostgresSaver.delete_thread` 删除，不直接修改官方表。
检查点和业务表使用不同连接，因此不声称两者共享一个数据库事务。
程序持有整个会话锁，先删除检查点，再修改业务文本：业务写入失败时原文本仍保留，下次运行可以据此重建上下文。
进程异常退出不会自动重放运行，也不保证模型答复和文本历史在故障瞬间同时落库；运行服务的其他限制仍见 [保留范围](agent-service.md#保留范围和当前限制)。

## 模块分工与实现依据

- `api/conversations.py` 定义不依赖 HTTP 的请求与分页结果；`api/runs.py` 定义任务提交与审批请求。
- `application/conversations.py` 通过存储和检查点协议实施版本校验、历史截断、互斥及权限边界。
- `application/service.py` 在已有 Agent 运行链内记录用户消息与最终答复，无检查点时输入保留的文本历史。
- `storage/postgres/conversations.py` 使用 Psycopg 参数化 SQL、行锁、版本字段和外键保存数据，不引入 ORM。
- `interfaces/agent_http.py` 校验 HTTP 请求，在线程中调用同步 CRUD 用例，再转换为 JSON；没有数据库 SQL 或另一套 Agent 循环。

官方检查点用于保存图执行状态，参见 [LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)。
它不能直接替代本项目需要的会话标题管理、版本冲突检查和独立于上下文裁剪的完整文本分页。
因此新增两个业务表和对应的最小用例，不自行实现检查点序列化、驱动或连接池。
维护成本是文本记录与检查点失效规则的同步；升级框架后需要验证审批恢复、清除及历史重建。
目前不导入该功能上线前已存在的全部检查点内容；已有会话在首次新运行或恢复审批时开始记录本次任务文本，旧内容继续只存在于原检查点。

集成测试位于 `tests/integration/test_conversations.py` 与 `tests/integration/test_agent_http.py`，
覆盖持久化、分页、范围隔离、版本冲突、真实 PostgreSQL 事务回滚、跨实例会话互斥、审批保护及上下文重建。
这些测试使用本机模型夹具，不代表外部模型效果验收。
