## 保留并说明的三条提示

### 重复取消时等待工具线程：S7497，一条

`tools/execution.py` 中的 execute_blocking 负责在线程退出后才允许调用方释放会话锁。
第一次取消会通知工具停止，然后等待线程收尾；这段等待再次被取消时，程序继续等线程，
收尾完成后仍通过外层 raise 传播取消异常。

直接在内部 except 中立刻抛出，会让调用方提前释放锁，而旧线程可能仍在写入同一会话。
因此保留此处控制流程，补充说明和重复取消回归测试，验证线程先完成清理、调用方随后收到 CancelledError。
该提示需要结合完整控制流人工复核，不能通过吞掉取消或强杀线程来消除。

### 本机工具服务使用 HTTP：S5332，两条

`interfaces/mcp_server.py` 中的 HTTP 地址用于允许的本机 Origin，服务只监听 127.0.0.1，
同时校验 Host、Origin 和服务令牌，并关闭代理头信任。这些地址不用于跨机器传输。
当前本机部署流程不引入证书管理，因此保留 HTTP；错误地址和未授权请求继续由集成测试覆盖。

如果以后开放远程访问，必须另行设计 TLS 和认证，不能直接把监听地址改成 0.0.0.0。
这两条提示应按本机部署前提人工复核，本次没有在 SonarCloud 上将它们标记为已解决。

## 自动分析与远程页面的边界

项目原先开启自动分析。官方扫描器不能与自动分析同时使用，因此复扫期间暂时关闭自动分析，
在保存工作区的问题列表和质量门禁结果后恢复，并核对原设置已经恢复。

恢复时，SonarCloud 会再次读取远程仓库；本次修复尚未提交和推送，
所以项目页面会重新显示远程旧提交的问题。上表记录的是包含本地修改的工作区分析结果。
修改提交并推送后，后续自动分析才会持续显示修复后的代码。
扫描器还提示无法确定部分代码行对应哪次 Git 提交，因此仍需由修复提交对应的自动分析确认远程结果。

[Sonar 官方文档](https://docs.sonarsource.com/sonarqube-cloud/analyzing-source-code/automatic-analysis#conflict-with-ci-based-analysis)
说明了两种分析方式不能同时使用的限制。覆盖率采集命令见 [开发指南](development.md#处理静态分析建议)。
